# 업데이트 노트 — 2026-02-20

## 주제: Gmail 동기화 API 호출 최적화 (조기 중복 필터링)

---

## 문제 원인

### 근본 원인

`fetch_tldr_emails()` 함수가 Gmail `messages.list()`로 메시지 목록을 가져온 뒤,
중복 체크(`newsletter_exists()`)를 하기 **전에** 모든 메시지의 full content를
`messages.get(format="full")`으로 다운로드하고 있었다.

```
[이전 흐름]
messages.list()          → [id1, id2, id3, ...] (가벼움)
messages.get(full) × N   → 모든 메시지 본문 다운로드  ← ❌ 낭비
newsletter_exists() 체크 → 이미 있으면 skip          ← ❌ 너무 늦음
```

### 왜 이런 구조였나?

기존 DB의 중복 키 컬럼(`email_id`)은 이메일 RFC 헤더의 **Message-ID 값**을 사용했다.
`messages.list()` 응답에는 Gmail 내부 ID(`{id, threadId}`)만 포함되고,
Message-ID 헤더를 얻으려면 반드시 `messages.get(format="full")` 이후에야 알 수 있었다.
따라서 중복 체크가 구조적으로 full content 다운로드 이후에 위치할 수밖에 없었다.

### 구체적 낭비 규모

| 시나리오 | full content 다운로드 횟수 |
|---------|--------------------------|
| 이전 (최근 7일, 50개 중 45개 기존) | 50회 |
| 이후 (동일 조건) | 5회 |
| **절감** | **45회 (90%)** |

재시작, 일별 스케줄 동기화, 수동 동기화 모두 해당. DB에 데이터가 쌓일수록 낭비 비율이 증가.

---

## 파급 효과 (수정 전)

1. **Gmail API quota 낭비**: `messages.get` 호출은 `messages.list`보다 무거운 API 호출.
   불필요한 호출이 쌓이면 일일 할당량(quota) 소진 위험.

2. **백엔드 재시작마다 불필요한 네트워크 트래픽**: `lifespan`에서 DB가 비어있지 않으면
   동기화를 실행하지 않지만, 수동 동기화(`POST /api/sync`) 시 매번 전체 다운로드 발생.

3. **동기화 시간 지연**: 이미 처리된 메시지를 전부 다운로드하므로 새 메시지 처리가 늦어짐.

## 수정 내용

### 수정 파일: `backend/app/services/db.py`

#### 1. `newsletters` 테이블 스키마 — `gmail_id` 컬럼 추가

```sql
-- 신규 DB (CREATE TABLE IF NOT EXISTS)
gmail_id TEXT UNIQUE

-- 기존 DB 마이그레이션 (_migrate_add_gmail_id())
ALTER TABLE newsletters ADD COLUMN gmail_id TEXT;
CREATE UNIQUE INDEX IF NOT EXISTS idx_newsletters_gmail_id ON newsletters(gmail_id);
```

- `gmail_id`: Gmail 내부 메시지 ID (messages.list 응답의 `id` 필드)
- nullable(`TEXT`, NOT NULL 아님): 기존 데이터와의 하위 호환 유지
- UNIQUE INDEX: NULL은 SQLite에서 UNIQUE 충돌 없음 → 기존 행 영향 없음

#### 2. `_migrate_add_gmail_id()` 신규 함수

서버 시작 시 `init_db()` 내에서 호출. 기존 DB에 `gmail_id` 컬럼이 없으면 자동으로 추가.
`PRAGMA table_info(newsletters)`로 컬럼 존재 여부를 확인하므로 멱등성(idempotent) 보장.

#### 3. `newsletter_exists_by_gmail_id(gmail_id)` 신규 함수

Gmail 내부 ID로 뉴스레터 존재 여부를 빠르게 조회하는 전용 함수.
조기 필터링에만 사용; 기존 `newsletter_exists(email_id)` 인터페이스는 변경 없음.

#### 4. `insert_newsletter()` — `gmail_id` 파라미터 추가

```python
# 변경 전
def insert_newsletter(email_id, published_date, articles) -> str

# 변경 후
def insert_newsletter(email_id, published_date, articles, gmail_id=None) -> str
```

기본값 `None`으로 기존 호출부 영향 없음.

### 수정 파일: `backend/app/services/gmail.py`

#### 5. `fetch_tldr_emails()` → 두 함수로 분리

| 함수 | 역할 |
|------|------|
| `_list_gmail_message_refs(days)` | `messages.list()`만 호출. `(service, message_refs)` 반환. full content 없음. |
| `_fetch_full_message(service, gmail_id)` | 단일 메시지의 `messages.get(format="full")` 호출. |

`service` 객체를 `_list_gmail_message_refs`에서 생성하여 반환하고,
`sync_emails()` 루프 안에서 재사용. 인증 오버헤드 최소화.

#### 6. `sync_emails()` — 조기 필터링 적용

```
[개선된 흐름]
_list_gmail_message_refs()          → [id1, id2, id3, ...] (가벼움)

for each gmail_id:
  newsletter_exists_by_gmail_id()   → 이미 있으면 즉시 skip  ← ✅ 조기 체크
  _fetch_full_message()             → 새 메시지만 다운로드    ← ✅ 필요한 것만
  newsletter_exists(email_id)       → 레거시 데이터 fallback 체크
  insert_newsletter(..., gmail_id)  → gmail_id 함께 저장
```

| 케이스 | 동작 |
|--------|------|
| 기존 데이터 (`gmail_id = NULL`) | `newsletter_exists(email_id)` fallback으로 중복 방지 유지 |

| 서버 재시작 (기존 DB) | `_migrate_add_gmail_id()` 자동 실행 → 컬럼 추가 후 정상 동작 |

## 주제 2: 서버 재시작 시 AI 재처리 방지 (Gemini 토큰 절약)

---

## 문제 원인

### 근본 원인

서버 재시작 후 `_resume_ai_processing()` → `run_ai_processing()`이 실행될 때,
`ai_processed = 0`인 기사를 가져오면 **이미 `summary_ko`, `category` 등 AI 데이터가 있어도**
무조건 Gemini API를 다시 호출하고 있었다.

또한 벡터 DB(`ChromaDB`)에 이미 임베딩이 존재해도 재임베딩 요청을 보냈다.

```
[이전 흐름 — 재시작 시]
get_unprocessed_articles()   → ai_processed=0 기사 전체
process_articles_batch()     → summary_ko 유무와 무관하게 Gemini 호출  ← ❌ 낭비
add_articles_to_vector_db()  → 벡터 DB 존재 여부 무관하게 임베딩 호출  ← ❌ 낭비
```

### 왜 이런 일이 발생하나?

AI 처리 도중 서버가 중단되면 `ai_processed`가 0인 채로 남는다.
재시작 후 `_resume_ai_processing()`이 이 기사들을 다시 처리하려 하는데,
이미 이전 실행에서 Gemini 결과가 DB에 저장된 경우라도 구분하지 않았다.

## 수정 내용

### 수정 파일: `backend/app/services/gemini.py`

#### `run_ai_processing()` — 기존 AI 데이터 재사용

배치를 가져온 뒤 두 그룹으로 분리:

| 그룹 | 조건 | 처리 방식 |
|------|------|-----------|
| `already_processed` | `summary_ko` 있음 | Gemini 호출 없이 `ai_processed=1` 마킹만 |
| `need_ai` | `summary_ko` 없음 | 기존과 동일하게 Gemini 호출 |

```
[개선된 흐름 — 재시작 시]
get_unprocessed_articles()

for each article:
  summary_ko 있음?
    ├── YES → Gemini 호출 스킵, ai_processed=1 마킹  ← ✅ 토큰 절약
    │         벡터 DB에 없을 때만 임베딩 추가         ← ✅ 중복 임베딩 방지
    └── NO  → 기존대로 Gemini 호출 후 저장
```

로그 예시:
```
기존 AI 데이터 재사용 5개 — Gemini 호출 스킵
AI 처리 완료: {'processed': 0, 'skipped': 45, 'failed': 0}
```

### 수정 파일: `backend/app/services/vector.py`

#### `is_article_in_vector_db(article_id)` 신규 함수

ChromaDB `collection.get(ids=[article_id], include=[])` 로 존재 여부만 확인.
임베딩 데이터를 가져오지 않으므로 가볍다.

```python
def is_article_in_vector_db(article_id: str) -> bool:
    result = _get_collection().get(ids=[article_id], include=[])
    return len(result["ids"]) > 0
```
